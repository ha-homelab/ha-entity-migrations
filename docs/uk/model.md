Усі документи використовують строгий JSON UTF-8. Дублікати ключів, нескінченні числові значення та NaN, невідомі поля схеми відхиляються. Точні приклади в `examples/` — виконуваний еталон. Поля версії мають містити ціле число `1`, не рядок чи логічне значення.

## Знімок

Верхній об'єкт містить лише `version` та `entities`. Кожна сутність містить рівно:

- `entity_id`: ID домену/об'єкта малими літерами, наприклад `light.workbench`.
- `hardware_id`: приватний непрозорий ідентифікатор, обраний оператором.
- `channel`: ідентифікатор фізичного каналу як рядок.
- `role`: унікальне логічне призначення, наприклад `workbench` чи `pump_enable`.
- `capabilities`: унікальні рядки з описом можливостей, наприклад `on_off`.

Пара обладнання/канал ідентифікує фізичну кінцеву точку. ID сутностей, фізичні точки та логічні ролі мають бути унікальними кожні у своїй множині. Фізичну діагностику представляйте іншим каналом, наприклад `rssi`, із власною унікальною роллю. Роль — планувальна мітка, а не область, мітка чи клас пристрою HA. Ці декларації не є вимірюваннями; засіб не може перевірити їх за обладнанням.

## Маніфест

Верхній об'єкт містить рівно `version`, `snapshot_sha256`, `sources`, `assignments` та `consumers`. `sources` зіставляє відносні імена файлів із хешами SHA-256. `assignments` містить повні замінні записи сутностей для фізичних точок, уже наявних у знімку. Неперелічені точки залишаються незмінними. Для нового пристрою спочатку внесіть до знімка його спостережувану резервну точку. Немає неявного створення чи видалення обладнання; ця версія вимагає унікальних ролей.

Кожен споживач визначає **літеральне рядкове значення** через `file` та RFC 6901 `pointer`. Екрануйте `/` як `~1`, а `~` як `~0`; індекси списків починаються з нуля без початкових нулів. Кожне знайдене посилання потребує явної політики:

- `follows_role`: знайти ціль, що володіє логічною роллю джерела.
- `follows_hardware`: зберегти фізичний канал джерела й використати його новий ID сутності.
- `retire`: запропонувати видалення явного об'єкта `retire_scope`, який містить посилання.

Невилучувані споживачі також потребують `kind` (`action`, `display`, `reference`), `allowed_roles` (непорожнє) та `required_capabilities` (може бути порожнім). Дії потребують `service_pointer`. Ці бар'єри захищають від використання насоса з новим призначенням як цілі освітлення. Це декларації, а не виведений намір.

Вилучувані споживачі мають рівно чотири поля: file, pointer, policy та retire_scope. Обсяг має бути об'єктом-предком, відмінним від кореня. Він може містити лише посилання на те саме вилучуване джерело; змішані чи динамічні посилання блокують його. Оберіть усю застарілу автоматизацію, якщо вилучення дії залишило б некоректну порожню послідовність. Засіб не запускає валідатор схеми HA.

## Зміни домену

Для дій між light/switch підтримуються лише `turn_on`, `turn_off`, `toggle` та відповідні сервіси `homeassistant.*`. Непорожні `data` чи `data_template` не приймаються для автоматичного перетворення сервісу. Доменний сервіс із кількома літеральними цілями блокується. Вказівник сервісу має володіти ціллю всередині своєї дії. Зміни домену відображення завжди потребують ручної перевірки функцій картки; вимикач не може непомітно успадкувати керування яскравістю.

## Межі

2 MiB на файл; разом 16 MiB вихідних файлів; 64 файли; 5000 сутностей, призначень чи споживачів; глибина JSON 40 і 100 000 вузлів значень на файл. Ідентифікатори — непорожні рядки до 256 символів, списки можливостей/дозволених ролей — до 64 унікальних рядків. Відносні шляхи джерел не можуть підніматися вгору, бути абсолютними чи містити символічні посилання. Входи — лише звичайні файли.

Завантажувач відхиляє два імені джерел, що ведуть до того самого канонічного шляху або ідентичності відкритого файлу (пристрій/inode). Сюди входять повторні роздільники, жорсткі посилання та регістрові псевдоніми на нечутливих до регістру файлових системах. Залиште одне ім'я й оновіть споживачів; псевдоніми не можуть нести різні політики міграції для одного фізичного файлу. Незалежні файли з однаковим вмістом залишаються коректними. Чистий API `plan` не має доступу до файлової системи: виклики, що самі будують відповідність джерел, мають забезпечити цю межу ідентичності перед зверненням до API.
